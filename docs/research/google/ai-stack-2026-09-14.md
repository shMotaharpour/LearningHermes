# Verification: Google AI Product Stack (as of 2026-09-14)

The most important, course-breaking finding is that **"Vertex AI" no longer exists as a standalone product name** — at Google Cloud Next '26 (April 22, 2026) Google renamed Vertex AI to the **Gemini Enterprise Agent Platform** ("formerly Vertex AI"), with the console migration completing May 21, 2026 and the old SDK modules scheduled for hard removal on June 24, 2026. Update the deck accordingly before teaching.

## TL;DR
- **Vertex AI → Gemini Enterprise Agent Platform** (rename + consolidation, GA April 22, 2026). "Agent Builder" was absorbed into this developer platform; the separate **Agentspace** product was folded into the employee-facing **Gemini Enterprise** app. The API endpoint (`aiplatform.googleapis.com`) is unchanged, and existing code/services carry forward under the new name.
- **Several other names in the deck are stale:** Vertex AI Search → **Agent Search**; Vertex AI Vector Search (formerly Matching Engine) → **Vector Search on Agent Platform**; the `vertexai.language_models` embedding SDK is deprecated (removal June 24, 2026) in favor of the **Google Gen AI SDK** (`google-genai`); recommended embedding model is now **gemini-embedding-001**.
- **Most Part B architectural claims hold**, but **Claim 2 is now largely FALSE** — Google's managed agent offering ships trajectory-level evaluation (six trajectory metrics), offline eval datasets, quality-alert regression gates, and Cloud Trace tracing.

## PART B — Claim verification

**CLAIM 1 — TRUE.** There are two access paths and the primary difference is governance. AI Studio API keys are personal/fast for prototyping; the Cloud path (Gemini Enterprise Agent Platform) adds IAM, service accounts, VPC-SC, audit logging, and per-project data handling. Crucially, the data-governance terms differ **by tier**: on the **free Google AI Studio tier and unpaid Gemini API quota**, Google's Additional Terms state content submitted "to the Services and any generated responses" is used "to provide, improve, and develop Google products and services and machine learning technologies," [Google AI](https://ai.google.dev/gemini-api/terms) and "human reviewers may read, annotate, and process your API input and output." [Google AI](https://ai.google.dev/gemini-api/terms) On the **paid Gemini API and the Cloud platform**, Google does not use prompts/responses for training. One exception: for users in the **EEA, Switzerland, or the UK**, the paid-services data terms apply to all services, including the free tiers. On the Cloud side, the training restriction is explicit: "Google won't use your data to train or fine-tune any AI/ML models without your prior permission or instruction. This applies to all managed models on Gemini Enterprise Agent Platform, including GA and pre-GA models." [Google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention) Zero data retention requires disabling the 24-hour input/output cache and requesting an abuse-monitoring exception. Sources: Gemini API terms — https://ai.google.dev/gemini-api/terms ; Gemini API ZDR — https://ai.google.dev/gemini-api/docs/zdr ; Cloud training restriction / ZDR — https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention

**CLAIM 2 — FALSE / OUTDATED.** Google's managed agent offering today has substantial evaluation, tracing and trajectory-inspection tooling. The **Gen AI evaluation service** provides final-response metrics plus six trajectory metrics — `trajectory_exact_match`, `trajectory_in_order_match`, `trajectory_any_order_match`, `trajectory_precision`, `trajectory_recall`, and `trajectory_single_tool_use` [Atamel](https://atamel.dev/posts/2025/06-30_genai_eval_service_overview/) (per Google's docs, "If the predicted trajectory is identical to the reference trajectory, with the exact same tool calls in the exact same order, the trajectory_exact_match metric returns a score of 1, otherwise 0"). [Google](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/evaluation-agents) Agent Platform's "Optimize" surface adds offline evaluations (a frozen task set), agent-behavior simulation, continuous evaluation with online monitors, configurable quality alerts (a regression gate), failure-cluster analysis, and Cloud Trace–based trace viewing. So all three capabilities the claim says you "lose" — a frozen task set, a regression gate, and trajectory-level visibility — are natively available. Sources: https://cloud.google.com/blog/products/ai-machine-learning/introducing-agent-evaluation-in-vertex-ai-gen-ai-evaluation-service/ and https://docs.cloud.google.com/gemini-enterprise-agent-platform/optimize/evaluation/agent-evaluation

**CLAIM 3 — PARTLY TRUE.** Managed retrieval is a reasonable default, but the managed products now expose more control than the claim implies. Agent Search supports **hybrid (semantic + keyword) search** and configurable answer generation, including abstention-style controls ("Ignore adversarial queries can stop generation of summaries that are unsafe or violate policy. Non-summary seeking queries stop generation of summaries that aren't helpful"). [Google](https://docs.cloud.google.com/generative-ai-app-builder/docs/release-notes?hl=en) The **RAG Engine** exposes chunking configuration ("Fine-tune RAG transformations"), Document AI layout and LLM parsers, and a dedicated reranking step. However, for a truly bespoke chunking strategy or a fully custom reranker/abstention rule, you will still end up building your own pipeline — so the claim's core intuition is directionally correct but overstated on chunking/ranking control. Sources: https://docs.cloud.google.com/generative-ai-app-builder/docs/release-notes and https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/rag-engine/retrieval-and-ranking

**CLAIM 4 — TRUE (with nuance).** The vector index layer is largely commoditized, and "pick based on where your data already lives" is sound default advice: pgvector on Cloud SQL/AlloyDB, BigQuery vector search for BigQuery-resident corpora, and dedicated Vector Search when scale demands it. But real capability differences exist. AlloyDB's ScaNN index materially outperforms plain pgvector HNSW at scale — per Google Cloud's benchmark, for indices that don't fit in main memory "the latency of pgvector HNSW is >4s … while ScaNN for AlloyDB delivers 10x better latency (431ms)," [Google Cloud](https://cloud.google.com/blog/products/databases/how-scann-for-alloydb-vector-search-compares-to-pgvector-hnsw) and ScaNN "builds indices for 1 billion vectors at up to 60x lower cost," [Google Cloud](https://cloud.google.com/blog/products/databases/how-scann-for-alloydb-vector-search-compares-to-pgvector-hnsw) with "a 4x smaller memory footprint" and "up to 4x better latency even for small datasets." [Google Cloud](https://cloud.google.com/blog/products/databases/how-scann-for-alloydb-vector-search-compares-to-pgvector-hnsw) BigQuery offers two index types (IVF for small query batches, TreeAH/ScaNN for large batches). Dedicated Vector Search remains best for very-high-scale, low-latency ANN. Sources: https://cloud.google.com/blog/products/databases/how-scann-for-alloydb-vector-search-compares-to-pgvector-hnsw and https://docs.cloud.google.com/bigquery/docs/vector-index

**CLAIM 5 — TRUE.** A2A (agent-to-agent) and MCP (agent-to-tool) are explicitly complementary, not competitors, and a system can use both. Google's stack supports MCP natively today in several forms: **ADK** supports MCP tools/servers; the **Gemini API/SDK** works with MCP servers via function calling; and **Agent Platform** provides Google-managed and custom **managed MCP servers** (with Apigee acting as an API-to-agent bridge). Both A2A and MCP now sit under the Linux Foundation's **Agentic AI Foundation (AAIF)**. Sources: https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation/ and https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/vector-search-2/use-agent-retrieval-mcp

## PART C — Code-level facts

**C1 — Embeddings: the posted code is DEPRECATED.** `from vertexai.language_models import TextEmbeddingModel` relies on the `vertexai.language_models` module, which Google deprecated on **June 24, 2025** and will remove on **June 24, 2026** ("SDK releases after June 24, 2026 won't include these modules. Use the equivalent namespaces from the Google Gen AI SDK, which has full feature parity"). [Google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/deprecations/genai-vertexai-sdk) The current recommended path is the **Google Gen AI SDK** — package **`google-genai`**, imported as `from google import genai` (replacing `google-cloud-aiplatform` for GenAI work; note the underlying REST endpoint is still `aiplatform.googleapis.com`).

The current recommended embedding model is **`gemini-embedding-001`** (it reached GA on May 20, 2025 and is the flagship; `text-embedding-005` is the older Gecko-generation English/code model and still available). Per Google's docs, `gemini-embedding-001` outputs **3072 dimensions by default**, truncatable via Matryoshka Representation Learning [CometAPI](https://www.cometapi.com/google-launches-gemini-embedding-001/) — Google recommends "using 768, 1536, or 3072 output dimensions" [HexDocs](https://hexdocs.pm/gemini_ex/embeddings.html) [Google AI](https://ai.google.dev/gemini-api/docs/embeddings) — with a **maximum input of 2,048 tokens** per text and pricing of "$0.15 per 1M input tokens" [TokenMix](https://tokenmix.ai/blog/gemini-embedding-001-dimensions-pricing-guide-2026) [Google Developers](https://developers.googleblog.com/gemini-embedding-available-gemini-api/) (batch is 50% off). On **maximum batch size**: the `gemini-embedding-*` family accepts **one input text per request** [GitHub](https://github.com/mem0ai/mem0/issues/6189) (use the Batch API for higher throughput); the older `text-embedding-005` accepts up to **250 text segments per request** (subject to a 20,000-token-per-call limit). [LangChain4j](https://docs.langchain4j.dev/integrations/embedding-models/google-vertex-ai/)

Corrected snippet (Gen AI SDK, Cloud backend):
```python
from google import genai
client = genai.Client(vertexai=True, project="your-project", location="us-central1")
result = client.models.embed_content(
    model="gemini-embedding-001",
    contents="What is the meaning of life?",
    # optional: config=types.EmbedContentConfig(output_dimensionality=768)
)
print(result.embeddings)
```
Docs: https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/deprecations/genai-vertexai-sdk ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/embeddings/get-text-embeddings ; https://ai.google.dev/gemini-api/docs/embeddings

**C2 — Terraform Cloud SQL private IP: the belief is CORRECT.** The two suspected-missing resources are indeed required. The complete minimal resource set (hashicorp/google v6.x) for a Cloud SQL instance with a **private IP** on a VPC is:
1. `google_compute_network` — the VPC (already declared).
2. `google_compute_global_address` — reserves an internal IP range for Google services (`purpose = "VPC_PEERING"`, `address_type = "INTERNAL"`). **(missing — required)**
3. `google_service_networking_connection` — establishes the private services access peering (`service = "servicenetworking.googleapis.com"`, `reserved_peering_ranges = [google_compute_global_address...name]`). **(missing — required)**
4. `google_sql_database_instance` — with `settings.ip_configuration.ipv4_enabled = false` and `private_network = google_compute_network...id`, plus `depends_on = [google_service_networking_connection...]`.

(Setting only `settings.ip_configuration.private_network` without the reserved range and the service-networking connection will fail, because there is no allocated peering range for Google's managed services network.) Minimal example (Postgres):
```hcl
resource "google_compute_global_address" "private_ip_address" {
  name          = "private-ip-address"
  purpose       = "VPC_PEERING"
  address_type  = "INTERNAL"
  prefix_length = 16
  network       = google_compute_network.peering_network.id
}

resource "google_service_networking_connection" "default" {
  network                 = google_compute_network.peering_network.id
  service                 = "servicenetworking.googleapis.com"
  reserved_peering_ranges = [google_compute_global_address.private_ip_address.name]
}

resource "google_sql_database_instance" "default" {
  name             = "private-ip-sql-instance"
  region           = "us-central1"
  database_version = "POSTGRES_14"
  depends_on       = [google_service_networking_connection.default]
  settings {
    tier = "db-custom-2-7680"
    ip_configuration {
      ipv4_enabled    = false
      private_network = google_compute_network.peering_network.id
    }
  }
}
```
Docs: https://docs.cloud.google.com/sql/docs/postgres/samples/cloud-sql-postgres-instance-private-ip (provider resource references: `google_compute_global_address`, `google_service_networking_connection`, `google_sql_database_instance` in the hashicorp/google provider).

## Caveats
- **Rapid rebrand artifacts:** as of Sept 2026 some official pages still show mixed old/new names (e.g., "Vertex AI Search is being renamed to Agent Search"; [Google](https://docs.cloud.google.com/generative-ai-app-builder/docs/data-governance) [Google](https://docs.cloud.google.com/generative-ai-app-builder/docs) product pages labeled "formerly Vertex AI"). The underlying services and `aiplatform.googleapis.com` endpoint are unchanged.
- **Governance page consolidation:** the legacy Vertex AI "Generative AI and data governance" page appears to have been restructured into the "zero data retention" and "abuse monitoring" pages under the new platform path; the exact "Generative AI and data governance" title now persists mainly for the separate Agent Search product (`generative-ai-app-builder/docs/data-governance`).
- **Data-retention nuance:** the 24-hour cache, abuse-monitoring logging, and a 30-day retention window (the 30-day figure specifically applies to "Advanced AI"–designated models such as certain Anthropic Claude models) [Google](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/abuse-monitoring) vary by product; reaching *zero* retention requires disabling caching and filing the abuse-monitoring exception.
- **A2A governance timeline:** A2A was announced by Google April 9, 2025, donated to the Linux Foundation June 23, 2025 [Google Open Source](https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html) (seeded with AWS, Cisco, Google, Microsoft, Salesforce, SAP, ServiceNow), [DEV Community](https://dev.to/googleai/google-cloud-donates-a2a-to-linux-foundation-162k) [Google Developers](https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation/) and per Axios (Aug 17, 2026) is becoming a hosted project of the **Agentic AI Foundation** [Axios](https://www.axios.com/2026/08/17/a2a-agentic-ai-foundation-open-ai-standards) (launched Dec 9, 2025, whose founding projects include Anthropic's MCP) — so A2A and MCP are now governed under the same foundation.
- **Source-quality note:** several dates and consolidation details (e.g., the exact April 22 / May 21 2026 milestones) are corroborated by Google's own name-changes doc and product pages plus multiple secondary outlets (The Next Web, Forbes); a few finer points (e.g., precise "last updated" footers on the ZDR/abuse pages) could not be captured verbatim and should be confirmed in-console.
